SDL Formulator: Formulation Cell Implementation Specification

V3.1 · architecture frozen31 October 2026Adds the agentic intelligence layer to V3; supersedes V2Audience: the implementing AI / automation engineer

This specification turns the V2 integration proposal into a buildable system. It keeps the V2 architecture (MADSci controls the cell, sdl_dt plans and learns, ROS 2 moves the robot, every instrument has its own node) and closes the gaps found in the senior engineering review: split ownership, the missing formulation compiler, an unsynchronized digital twin, no failure handling, no data model, and an undefined optimization problem. V3.1 adds an agentic intelligence layer (five agents on LangGraph, an MCP tool server, Pydantic contracts, an LLM gateway and evaluation-gated CI/CD) that assists people without ever gaining a path to the hardware. Every decision the review left open is made here and recorded as an architecture decision (ADR). Anything marked set at commissioning is a measured value, not an open design choice.

MADSci executes. sdl_dt thinks. Agents assist. ROS 2 moves. The safety system protects.

sdl_dt is a client of MADSci, never a second control system. MADSci is the only component that authorizes physical execution. The digital twin can reject a plan but can never, on its own, make one safe: safety-rated limits, guarding and the E-stop stay independent of all software in this document. The optimizer proposes experiments; it never touches hardware. Agents draft, explain and analyse through the same permission-checked APIs a person uses; no agent tool reaches a node, a device, ROS 2 commands or the safety configuration.

1. Architecture decisions

These close the five open items of V2 and the review’s seven questions; ADR-15 to ADR-20 add the agentic layer. Changing any of them requires a new ADR approved by the technical lead; the implementer builds against them as written.

3. Execution pipeline

Ten stages replace V2’s six. New in V3: an explicit compile stage, scheduling inside MADSci, an approval stage, a per-action execution gate that re-checks state, and a verify stage so the optimizer learns only from measured values. Every stage can stop the run, and every stop produces a reason code stored with the experiment.

4. Formulation compiler

formulation_engine is a pure Python library with no hardware or network access, so it can be built and tested before any hardware is ready. It turns a formulation into a machine-specific process plan, or rejects it with machine-readable reasons. It is the first build priority.

Compile steps, in order

  1. Schema check. Parse with the Pydantic model; reject unknown fields and unsupported major versions.
  2. Composition check. Mass fractions sum to 1 within 1×10−6; every fraction is within the campaign’s bounds.
  3. Target masses. targeti = batch_mass_g × fractioni, rounded to the balance readability. 5.0 g gives 2.000, 0.750 and 2.250 g.
  4. Material resolution. Look up each material: phase, allowed dispenser types, density, viscosity range, current lot and quantity on hand (from the Resource Manager).
  5. Equipment selection. For each ingredient, choose a compatible dispenser whose minimum mass and repeatability support the target and tolerance.
  6. Addition order. Use the spec’s order if given; otherwise powders before liquids, largest powder first, to limit tool changes.
  7. Expand into actions from the template: tool change, tare, dispense, read mass, transfer, mix, return. Add mass-correction and verification steps.
  8. Process envelope. Mixing speed, duration and container fill level are within the mixer’s limits; batch mass fits the container.
  9. Emit the ProcessPlan, the MADSci workflow, the resource list and the required records, plus a deterministic hash of all inputs.

5. Workflow and scheduling

The compiler produces the workflow (what happens, in what order); the MADSci scheduler produces the schedule (when, and which devices work at the same time). sdl_dt no longer schedules.

Scheduling model

  • Jobs: one per sample; tasks: the process-plan steps with their after dependencies.
  • Renewable resources, capacity 1: gantry zone, arm, each balance, mixer, each container, each dispenser.
  • Setup times: tool change on the gantry, mixer lid open and close.
  • Transfer constraints: a container is held by exactly one location or the gripper at any time.
  • Shared-zone exclusion: gantry and arm tasks that list the same zone cannot overlap.
  • Durations: p90 of the last 50 measured runs of that action and argument class; configured estimate until 20 samples exist.
  • Objective: minimize makespan, then total container waiting time (limits time a mixed sample sits before characterization).
  • Re-planning: on any delay over 20 % of a task’s p90, or on a fault, re-solve the unstarted tasks with current state.

Scheduler interface

class Scheduler(Protocol):
    def solve(self,
              plans: list[ProcessPlan],
              resources: ResourceModel,
              durations: DurationModel,
              now: datetime,
              hints: SchedulingHints | None = None,
              ) -> Schedule: ...

# Schedule.entries: action_id, step_id, node,
#   start, end, resources, zone
# Schedule.solver: "cp-sat" | "list-fallback"
# Schedule.makespan_s, Schedule.optimal: bool

CP-SAT runs with a 2 s limit; if it returns no feasible solution in time, the critical-path list scheduler runs. Both are deterministic for a given seed and input, so a schedule can be reproduced from its stored inputs.

6. Digital twin as a synchronized validation service

Principle. A successful simulation is evidence that the modeled constraints hold. It is not proof that physical execution is safe. The twin can block execution; it can never be the only thing allowing it.

Cell-state synchronization and scene versions

  • cell_state_manager (new ROS 2 package) is the single owner of the scene: UR3e joint states from the driver, gripper state, gantry position from the weighing node, mixer lid state from the mixer node, and container locations from the MADSci Location Manager.
  • The scene is divided into zones (zone_gantry, zone_mixer, zone_drop, zone_balance_1, zone_balance_2). Each zone has a monotonically increasing version; the global scene_version increments on any change.
  • Robot joint motion inside a reserved trajectory does not bump versions; any untracked motion, object move, lid change or gantry move does.
  • In Real mode the scene follows the real cell (digital shadow); in Fake mode it follows the virtual devices. The mode is part of the snapshot.
  • If a source stops publishing for more than 1 s, its zones are marked unknown and no verdict depending on them can be validated.

The 10 mm and 20 mm clearance thresholds and the 5° joint margin are the initial values for the UR3e with the current gripper. They are configuration, reviewed at commissioning, and stored in each verdict’s checks.

Invalidation rules at the execution gate

  1. Every zone in zone_versions still has the same version, and none is unknown.
  2. now < expires_at (verdicts live 120 s).
  3. model_hash equals the currently loaded model.
  4. The action’s reservation lease is still held by this experiment.
  5. The device reports its own interlocks true and the cell is armed (Real mode).

If rule 1, 2 or 3 fails, the gate requests a fresh dynamic validation once. If that is not validated, the action is blocked and the experiment goes to FAULT with the verdict’s reason codes.

7. Execution state machine and recovery

Experiments and actions each have an explicit state machine, owned by MADSci and persisted on every transition, so a restart resumes from stored state. Every transition emits an event to the Event Manager.

Action states

PENDING → AUTHORIZED → DISPATCHED → RUNNING → SUCCEEDED
                                        ↘ FAILED
           (timeout or lost link)       ↘ UNKNOWN → reconcile
                                                   → SUCCEEDED | FAILED

UNKNOWN is a first-class state: after a timeout the action is neither retried nor assumed done. MADSci calls the node’s get_action_status(action_id); if the node cannot answer, the action stays UNKNOWN and the experiment goes to FAULT.

Idempotency rules (ADR-09)

  • Each dispatch carries action_id and idempotency_key = hash(experiment_id, step_id, attempt).
  • The node writes the key to its local ledger (SQLite) before sending a device command, and the result after.
  • A repeated key returns the stored result and never commands the device again.
  • Actions are classed: read (read mass, get state: safe to repeat), positioning (move to a pose: repeatable after state check), material-changing (dispense, transfer, mix: at most once).
  • A new attempt of a material-changing action needs a new attempt number, issued only by the recovery procedure.

Recovery procedure

  1. Enter FAULT: stop dependent actions, hold all leases, record the triggering event and reason code.
  2. Enter RECOVERING: query every device involved; resolve every UNKNOWN action to SUCCEEDED or FAILED from device evidence.
  3. Update the Location Manager and the scene from verified positions; anything that cannot be verified needs operator confirmation in the sdl_dt recovery view.
  4. The operator chooses: re-plan the remaining actions (back to PLANNED, then full validation) or abort (release leases, move containers to a safe location, ABORTED).
  5. Record the full recovery trail as events linked to the experiment.

Observation validity, for training

  • valid: completed, all masses within tolerance, calibration valid, mode real. Used for objectives.
  • deviated: completed with recorded deviations. Used with the actual composition, never the commanded one.
  • failed_process: the formulation could not be prepared or mixed (for example phase separation, dispensing impossible). Used only by the feasibility model.
  • failed_equipment: an equipment or software failure unrelated to the formulation. Excluded from all models.
  • excluded: removed by a scientist with a written reason. Excluded.
  • simulated: Fake-mode results. Never mixed with real data; used only for pipeline tests.

The optimizer always trains on actual measured compositions and properties. A run with incomplete provenance is automatically excluded.

10. Formulation-aware optimization

The optimization problem, defined so it can be implemented in sdl_dt/optimization with BoTorch and Ax (ADR-12). The objective set is chosen per campaign by the scientist; the machinery below is fixed.

ElementDefinition
Decision variablesMass fractions x1…xk of the campaign’s ingredients; mixing speed (rpm); mixing duration (s); defoaming duration (s). Process bounds come from the equipment capability file, never hard-coded.
Mixture constraintΣ xi = 1, li ≤ xi ≤ ui. Implemented by optimizing over k − 1 free fractions with the linear inequality Σi<k xi ≤ 1 − lk, the last fraction derived.
Manufacturability constraintbatch_mass × xi ≥ min_dispense_g of its dispenser for every present ingredient; every candidate passes the compiler dry run before it is proposed.
Objectives1 to 4 per campaign, each with direction and a reference point, for example: maximize API solubility, maximize permeability, minimize viscosity, minimize preparation time.
Outcome constraintsFor example viscosity ≤ dispensing limit, stability ≥ threshold; modeled as GP outputs with a probability-of-feasibility weight.
SurrogateIndependent GP per objective, Matérn 5/2 kernel with ARD, inputs normalized to [0, 1], outputs standardized, heteroscedastic noise when replicate data exist. Random-forest ensemble as an explainable baseline.
Feasibility modelGP classifier on valid vs failed_process observations; candidates weighted by P(feasible) and filtered at P < 0.2.
AcquisitionqNEHVI (noisy expected hypervolume improvement) for 2+ objectives; qLogNEI for a single objective. Batch q = 1 to 4, matched to how many samples the schedule can run in parallel.
Initial design12 points (or 2(d + 1), whichever is larger): space-filling Sobol samples projected onto the constrained simplex, plus the reference formulation and its 2 replicates.
ReplicatesThe reference formulation repeats every 10 experiments to monitor drift; a drift beyond 2σ pauses the campaign.
StoppingBudget reached, or hypervolume improvement below 1 % over 3 consecutive batches, or the scientist stops the campaign.
Human in the loopThe scientist can approve, edit or replace each proposed batch; edits are stored with origin scientist.
maximizex, p   f(x, p) = [f1, …, fm]    subject to   Σ xi = 1,   li ≤ xi ≤ ui,   p ∈ Pequipment,   gj(x, p) ≤ 0,   compile(x, p) = ok
next batch = argmaxq candidates   qNEHVI(x, p) · P(feasible | x, p)

Evaluation before hardware

  1. Build a synthetic benchmark with the same variable structure (mixture plus process parameters) and known optimum.
  2. Compare constrained qNEHVI against Sobol sampling and a classical mixture DoE (simplex-centroid) over 10 seeds and the same budget.
  3. Pass criterion: qNEHVI reaches 90 % of the benchmark’s maximum hypervolume with at least 30 % fewer experiments than the best baseline, averaged over seeds.
  4. Replay historical or Fake-mode runs end to end to test the data pipeline, validity flags and proposal flow.

11. Agentic intelligence layer

Five agents built with LangGraph, MCP and Pydantic help scientists, operators and engineers work faster: they turn goals into campaign drafts, explain what the cell is doing, propose recovery options and write the analysis. The deterministic components keep every decision that matters: the compiler decides what can be made, the optimizer decides what to try, the validation service and execution gate decide what may move, and people approve. The agent layer lives in a new package, sdl_agents, alongside sdl_dt.

Rule (ADR-15). An agent can only do what its MCP tools allow, with the permissions of the person it serves. There is no tool for device commands, ROS 2 goals, editing capabilities or safety configuration, arming the cell, or approving anything. A prompt injection or a model error can therefore produce, at worst, a bad draft that a person and the compiler will reject.

Guardrails

  • Structural: forbidden actions have no tool (ADR-15); the allowlist is enforced in sdl_mcp, not in the prompt.
  • Identity: every tool call carries the user’s token; an agent can never do more than the person it serves.
  • Prompt injection: retrieved documents, comments and record text are wrapped as data; tool results never become system instructions; the red-team suite in CI tests this.
  • Grounding: AG-2, AG-4 and AG-5 must cite record IDs or document sections; an answer without a source says it has none.
  • Budgets: step, token, time and cost limits per run and per day; exceeding them stops the run with a message.
  • Provenance: each run is an AgentRun record (agent, graph version, prompt version, model, route, tools called, inputs and outputs by reference, user) linked to every draft, proposal or submission it produced.
  • Kill switch: one configuration flag disables all L2 and L3 tools; the deterministic system keeps running without agents.

  1. The scientist states the goal; AG-1 drafts the campaign (target properties, ingredients, bounds, budget) and the scientist approves it.
  2. The optimizer proposes a formulation; the compiler dry run confirms it can be made.
  3. MADSci compiles the process plan, validates materials and equipment, and schedules it.
  4. The digital twin validates every motion against the current cell state.
  5. The approved workflow runs on the real equipment through the execution gate.
  6. Measurements are verified and stored with full provenance.
  7. The optimizer updates its models and proposes the next experiment, with no manual data handling.
  8. AG-4 drafts the campaign report, AG-2 answers the scientist’s questions about it, and every agent step is traceable in its AgentRun record.

18. Glossary

Self-driving lab (SDL)
A lab that plans, runs and learns from its own experiments, with robots and AI in a closed loop.
Formulation specification
The recipe: ingredients, mass fractions, batch mass, tolerances and process conditions.
Formulation compiler
Turns a formulation into a machine-specific process plan, or rejects it with reason codes.
Process plan
The ordered, typed actions, resources and records needed to prepare one formulation on this cell.
Workflow (storyline)
The process plan as a MADSci workflow: a directed acyclic graph of node actions.
Schedule
Start and end time of every action, and which run in parallel.
Makespan
Total time from the first action to the last.
Reservation lease
A time-limited exclusive claim on a resource, held from scheduling through execution.
Scene version
A counter that changes whenever the modeled cell state changes; verdicts are valid only for the versions they were computed on.
Static validation
Checks that depend only on geometry and limits, computed once per route.
Dynamic validation
Checks against the current cell state, computed per action.
Execution gate
The last check before an action runs: fresh verdict, held lease, true interlocks, armed cell.
Idempotency key
An identifier that lets a node recognize a repeated command and return the earlier result instead of acting again.
Digital shadow
A live view of the real machines driven by their telemetry.
Interlock
A condition that must hold before an action may start, such as the mixer lid being closed.
Bayesian optimization
Proposes the next experiment from a probabilistic model, balancing exploration and exploitation.
qNEHVI
Noisy expected hypervolume improvement for batches: the acquisition function for multi-objective campaigns.
Agent
An LLM-driven workflow that plans steps and calls tools to help a person; here it never commands hardware.
Autonomy level
L0 inform, L1 draft, L2 act digitally, L3 submit within an approved campaign.
MCP (Model Context Protocol)
An open protocol for exposing tools and data to LLM applications; sdl_mcp is the cell’s tool server.
LangGraph
A library for building agents as explicit state graphs with checkpoints and human-approval interrupts.
LLM gateway
A single proxy for all model calls that routes, logs and enforces which data may reach which model.
Data class
C0 public to C3 restricted; decides which model endpoints may see a piece of data.
Prompt injection
Text in a document or record that tries to make an agent follow it as instructions.
Evaluation suite
A fixed set of tasks with reference answers that scores an agent before a change ships.
Provenance
The record of where every result came from: formulation, materials, plan, devices, calibrations, verdicts and software.
